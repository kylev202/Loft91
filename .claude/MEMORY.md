### 1.2 What the venue *is* — the positioning read

Derived from the name, the wordmark, the upstairs location and the dual bar/hire model.
Held as an **interpretation**, not a fact, and used only to steer `DESIGN.md`:

- A **loft** — upstairs, above the street, a room you have to know about and climb to.
  Discovery and intimacy are the product, not volume.
- **Weekend-only, night-weighted.** Fri/Sat evenings and a Sunday afternoon. The site's
  emotional register is night: low light, warm metal, dark rooms.
- **Two audiences, one venue.** (a) the walk-in drinker deciding where to go tonight, and
  (b) the function organiser deciding where to put 40 people in six weeks. These need
  different journeys off the same homepage. See §3.2.

## 3. The client brief

### 3.1 As stated (verbatim intent, from the original brief)

> A minimalism website with smooth scrolling effect, animation, and professional design.
> Their logo animated in the loading page. Aesthetic homepage that clearly shows their
> branding. Uses professional fonts and combination of fonts. They want **menu**,
> **packages**, **gallery** — all have to follow a unique theme and style.

### 3.2 Decomposed into requirements

| ID | Requirement | Type | Acceptance signal |
|---|---|---|---|
| R1 | Minimalist visual language throughout | Non-functional | Passes the `DESIGN.md` §9 banned-defaults audit; no section survives that could be dropped into another venue's site unchanged |
| R2 | Smooth scrolling across the whole site | Functional | Inertial scroll present on desktop; native scroll preserved on touch; disabled under `prefers-reduced-motion` |
| R3 | Animated logo on a loading page | Functional | Per-letter wordmark animation, ≤1.4 s, non-blocking, shown once per session |
| R4 | Homepage that reads as *this* venue | Functional | Above-the-fold answers: what it is, where it is, when it's open, how to book |
| R5 | Professional type system — a *combination* of fonts | Non-functional | ≥2 families with a deliberate contrast role split; zero banned fonts (`DESIGN.md` §9) |
| R6 | Menu section/page | Functional | Real menu data rendered; no `[TBC]` in production |
| R7 | Packages section/page (functions & venue hire) | Functional | Package tiers + an enquiry path that reaches the venue |
| R8 | Gallery section/page | Functional | Real venue photography, lazy-loaded, LCP-safe |
| R9 | One coherent theme across R6–R8 | Non-functional | Menu, Packages and Gallery share tokens, motion grammar and section rhythm — verified side-by-side, not page-by-page |
| R10 | Professional, production-grade execution | Non-functional | Meets the `DESIGN.md` §11 performance and §10 accessibility budgets |

### 3.3 Requirements *implied* by the venue but not stated by the client

Flagged so the Planner raises them rather than silently building or silently omitting them:

- A **find-us / contact** surface — address, map link, hours, socials. R4 depends on it.
- A **functions enquiry mechanism**. Today the only channel is Instagram DM. A website
  that only says "DM us" wastes the site's main commercial job. See §6 Q3.
- **Mobile-first reality.** Traffic will arrive from an Instagram bio link on a phone,
  at night, on mobile data. Mobile is the primary target, not the fallback.
